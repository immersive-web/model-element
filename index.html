Abstract

The model element allows embedding 3D graphical content inline within an [HTML] document to be managed declaratively, and rendered directly by the user agent. The HTMLModelElement interface then provides a simple API for controlling the presentation, animation, interaction, fetching, and UI affordances of a model.

1. Introduction

The HTML model element allows a website to embed interactive 3D models as conveniently as any other visual media. Models are served as a standalone resource. The model element also has support for interaction and animation playback while presented within the page, and supports more spatial experiences, such as the stereoscopic display of 3D content where available.

As model is rendered directly by the user agent, it has the ability to utilize privileged information, such as the user’s head and eye position or the lighting of the user’s environment, without exposing that information to JavaScript. Additionally, the use of accessibility information and controls can be engaged in a privacy-preserving manner.

As model is embedded content, the user agent can present 3D content in a privacy-preserving, interactive, and accessible manner.

2. Out of scope

There are a number of specified non-goals for this initial incubation; some are beyond the long-term scope of this proposal, and others are deferred for the benefit of reaching consensus on an initial specification, which can hopefully serve the needs of users and authors sooner.

2.1. Scene graph inspection and manipulation

While the use cases for inspecting and manipulating the contents of a given model asset are clear, the initial scope of this proposal is intentionally limited to a reduced complexity, hopefully making the initial specification one that has broad consensus amongst the web community.

2.2. Animation mixing and blending

While many popular model formats include the ability to encode, play and mix multiple animations in an animation mixing system, This initial specification considers only a single animation timeline, both for simplicity and for having a minimal viable specification on which the web community can build on.

2.3. Stateful interaction with model contents

While many popular model formats support tapping on a 3D button inside their contents to show or hide additional contents like a title, play an animation or undertake some other stateful action. Because there is no current intention to provide a JavaScript-facing mechanism to be aware of such actions, stateful interactions should be considered out of scope.

2.4. Subresource loading

While many popular model formats support the use of external asset requests for better re-use and consistency, this initial specification will only allow assets that are self-contained.

3. Examples

3.1. Adding a model to a document

The following example shows the simplest way to add a 3D model to a document:

<model src="3d-assets/car"></model>

By using content negotiation the user agent relies on the server to send back a 3D model in a format the user agent supports.

3.2. Enabling orbit stage mode

The following example shows the syntax for enabling the standard "orbit" mode:

<model stagemode="orbit">
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
</model>

3.3. Supporting multiple formats

The following example shows a list of potential source formats that can be selected from:

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
</model>

model source selection follows video selection, where the top-level src attribute takes precedence if present, followed by the first compatible source element encountered.

3.4. Providing fallback content for legacy user agents

The following example supplies fallback content for user agents that do not yet support the element:

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
  <img src="image-assets/teapot.png">
</model>

3.5. Making model accessible

The following example supplies alt text information for both the model content and fallback content, in the event that model is not supported on the target user agent.

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.usdz+zip">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
  <img src="image-assets/teapot.png" alt="A teapot">
</model>

3.6. Providing a loading preview and fallback content

The poster provides an image preview while the model loads. The fallback content is displayed if the model cannot be loaded, loading is blocked, or the browser does not support model. A picture in the fallback content can select images for different color schemes and formats:

<model src="3d-assets/teapot.usdz" poster="image-assets/teapot-preview.png">
  <picture>
    <source media="(prefers-color-scheme: dark)"
            srcset="image-assets/teapot-dark.avif" type="image/avif">
    <source srcset="image-assets/teapot-light.avif" type="image/avif">
    <img src="image-assets/teapot.png" alt="A ceramic teapot">
  </picture>
</model>

DOM Interface

The HTMLModelElement interface provides a means to interface with the embedded resource.

[Exposed=Window, SecureContext]
interface HTMLModelElement : HTMLElement {
  [CEReactions, Reflect] attribute unsigned long width;
  [CEReactions, Reflect] attribute unsigned long height;
  [CEReactions, Reflect] attribute boolean autoplay;
  [CEReactions] attribute DOMString? crossOrigin;
  [CEReactions, ReflectURL] attribute USVString poster;

  readonly attribute Promise<HTMLModelElement> ready;
  readonly attribute DOMPointReadOnly boundingBoxCenter;
  readonly attribute DOMPointReadOnly boundingBoxExtents;

  attribute DOMMatrixReadOnly entityTransform;

  attribute USVString environmentMap;
  readonly attribute Promise<undefined> environmentMapReady;

  [Reflect=stagemode] attribute DOMString stageMode;
};

The model element is used for embedding 3D models into a document. Its model-specific APIs, resource processing, and rendering are restricted to secure contexts, as specified in § 16.1 Secure contexts.

Content may be provided inside the model element as fallback content. The element MUST represent this content when model loading is blocked or fails, as specified in § 8.3.2 Poster display. It is also intended for browsers that do not support model. User agents MUST NOT show the fallback content while the model is loading or while available model content is displayed.

4.1. autoplay attribute

The autoplay attribute is a boolean attribute that controls whether the model’s animation starts automatically when a new model resource is loaded. The autoplay IDL attribute MUST reflect the content attribute.

After the initial bounds calculation and fitting for a newly loaded model resource, and before resolving ready, the user agent MUST initialize model animation playback for the element.

To initialize model animation playback for a model element element:

  1. If element’s loaded model resource contains no animation, return.

  2. Set the animation to its first frame and initialize playback in the paused state.

  3. If element has an autoplay attribute, begin animation playback.

After playback has been initialized, adding, removing, or changing autoplay MUST NOT by itself start, pause, or restart the current animation. Its value is used when initializing a subsequently loaded model resource; recreating a renderer for the same resource MUST NOT reapply autoplay in place of the resource’s existing playback state.

Note: Autoplay controls initial animation playback and does not require eager resource loading. A user agent can still defer loading an offscreen model.

4.2. stagemode attribute

The stagemode attribute determines the model’s stage mode. It is an enumerated attribute. The none keyword selects the none mode, and the orbit keyword selects the orbit mode. Its missing value default and invalid value default are the none state.

Changes to the selected mode MUST apply the behavior defined in § 6 Interaction and § 8.2.4 Automatic fitting after resize. The stageMode IDL attribute MUST reflect the stagemode content attribute.

4.3. controls attribute

4.4. crossorigin attribute

The crossorigin attribute is a CORS settings attribute. It controls request credentials using HTML’s CORS settings attribute credentials mode, as specified in § 16.2 CORS.

The crossOrigin IDL attribute MUST reflect the crossorigin content attribute, limited to only known values.

4.5. height attribute

The height attribute, if specified, MUST have a value that is a valid non-negative integer. It gives the desired vertical dimension of the model element in CSS pixels. Zero is permitted.

4.6. loading attribute

Some model’s resources can be significant in size. As such, it might be good to support the loading attribute to allow these resources to be lazy-loaded. GitHub issue #44: Lazy loading.

4.7. loop attribute

4.8. poster attribute

The poster attribute gives the URL of an image file that represents the model and is displayed before the model is ready to display. The attribute, if present, MUST contain a valid non-empty URL potentially surrounded by spaces.

Each model element has a poster frame that is an image or null, initially null.

When a model element is created, or its poster attribute is set, changed, or removed, the user agent MUST determine a model poster frame for the element, regardless of whether the poster is currently displayed. A change to the document’s base URL alone MUST NOT restart this algorithm.

To determine a model poster frame for a model element element:

  1. Abort any existing instance of this algorithm for element without changing its poster frame. Results from an aborted instance MUST NOT subsequently change the poster frame.

  2. If element’s poster attribute is absent or its value is the empty string, set element’s poster frame to null and return.

  3. Let url be the result of encoding-parsing a URL given the poster attribute’s value, relative to element’s node document.

  4. If url is failure, set element’s poster frame to null and return.

  5. Let request be a new request whose URL is url and destination is "image".

  6. Configure a model request given request and element.

  7. Fetch request. This MUST delay the load event of element’s node document until this instance of the algorithm completes or is aborted.

  8. When fetching and image decoding complete, if an image is obtained, set element’s poster frame to that image. Otherwise, set it to null.

Loading or changing a poster image MUST NOT interrupt available model content. The poster’s availability MUST NOT be a condition for resolving ready, and a failure to fetch or decode the poster MUST NOT reject that promise or cause the element to display its fallback content.

The poster IDL attribute MUST reflect the poster content attribute as a URL.

Note: Poster URL parsing, cancellation, and load-event behavior follow the poster-frame retrieval rules for <video> in [HTML]. Request construction follows § 16.2 CORS, and poster display follows § 8.3.2 Poster display. The loading attribute’s lazy-loading behavior remains to be defined in GitHub issue #44.

Like poster, poster accepts a single image URL. Should model loading previews also support alternative formats, resolutions, aspect ratios, or color schemes, or richer placeholders such as another model? A picture in fallback content supports image selection after a model fails, but does not provide a responsive loading poster. See GitHub issue #130: What role, if any, should poster play?.

4.9. src attribute

4.10. width attribute

The width attribute, if specified, MUST have a value that is a valid non-negative integer. It gives the desired horizontal dimension of the model element in CSS pixels. Zero is permitted.

5. source element integration

5.1. The source element’s parent is a model element

The source element behaves differently depending on who the parent is. For instance, when the parent is picture, the srcset attribute comes into to play. We need to look at the attributes of source and figure out what they mean in when used in the context of model. GitHub issue #24: Specify the behavior for when a <source> element’s parent is a <model> element.

6. Interaction

In addition to emitting standard input events, model may interpret input events according to specific stage modes, including none and orbit.

6.1. none

The default stage mode. In this mode, input events do not have any direct action on the behavior of the element.

6.2. orbit

In this mode, input events in a horizontal direction result in a rotation of the model about the Y axis, and events in a vertical direction result in a rotation about the horizontal axis. This is reflected in the model’s entityTransform value.

In this mode, the entityTransform value is read-only.

Setting the mode to orbit results in a change of the position and scale to the orbit fit mode.

glTF is not a run-time format. It does not define what an application should do with a model once it is loaded and rendered. It does provide some capabilities that a run-time engine may use to enhance the user experience. glTF currently does not store any interactivity information. Currently that is solely a run-time determination. The run-time determines what parts (if any) of the model may be active and the behavior based on any trigger. Like Interactivity, animation is not built-into glTF. glTF files may contain animation parameters that specify the type of animation (e.g., morph, skin & bones, etc.) and the associated parameters needed to perform the animation. There is nothing in the glTF specification that defines how one animation interacts with another. For example, a human model may include walk, jump, and drop animations; but it is unlikely that they should all be played at the same time. Any HTML element that wishes to handle animation as stored in a glTF file needs to understand how the content creator intended the animation to play. GitHub issue #2: Dealing with format specific animations and Interaction.

7. Controls

As with other media elements (again #13), having "controls" for media specific things can be extremely helpful for accessibility (and just generally helpful for developers not needing to deal with things like the fullscreen API). It would be nice to consider adding support for controls and then leaving it mostly to the UA as to what those controls are... we could figure out a standard set of things, like video provides. GitHub issue #43: Adding "controls".

8. Rendering

The model SHOULD be rendered according to a realtime, physically-based rendering (PBR) shading model, and lit by an image-based light.

8.1. Environment map

If provided, an environment map MUST be interpreted as an equirectangular environment map. If an environmentMap is not specified, the User Agent MUST provide an appropriate map.

8.2. Model pose

The position, rotation, and scale of a displayed model MUST present its contents according to its entityTransform property, a DOMMatrixReadOnly that can be composed using that object’s existing API.

The point and matrix interfaces and their operations are defined in [GEOMETRY-1].

Each model element has a stored entity transform, initially a DOMMatrixReadOnly representing the identity matrix with is2D set to false.

For the setter steps below, an element’s model renderer is the user agent’s internal instance that manages loading and rendering the element’s model, or retained rendering state used while rendering is suspended. It is null until such an instance is created, and becomes null when that instance and its retained state are discarded. A renderer can exist before ready resolves; its existence does not require the model to be visible.

Updates to the entityTransform SHOULD be reflected on the next rendered frame.

The entityTransform getter steps are:

  1. Return this element’s stored entity transform.

8.2.1. Restrictions on script-assigned transforms

A matrix assigned to entityTransform by script MUST be representable as a composition of scale, rotation, and translation, without shear or perspective. Its scale factors MUST be non-zero and uniform across the X, Y, and Z axes: the scale factors in that decomposition MUST have the same sign and magnitude. All matrix components MUST be finite.

When validating a matrix, the user agent MAY account for floating-point rounding in the scale factors and in reconstructing the matrix from its scale, rotation, and translation. It MUST NOT replace an unsupported matrix with an approximation that discards non-uniform scaling, shear, or perspective.

The entityTransform setter steps, given value, are:

  1. Let element be this model element.

  2. If element is in orbit mode, throw an InvalidStateError exception.

  3. If element’s model renderer is null, throw an UnknownError exception.

  4. Let matrix be a copy of value’s 16 matrix components.

  5. If matrix does not satisfy the matrix restrictions above, throw a NotSupportedError exception.

  6. Update the model entity transform for element, given matrix.

  7. Set element’s automatic fitting enabled flag to false.

If the setter throws, the stored entity transform and automatic fitting enabled flag MUST remain unchanged. The model MUST continue to use its previous transform.

These validation requirements apply to script assignments. They do not prevent the user agent’s fitting algorithms from producing a zero scale when an element has a zero-sized viewport, as specified below.

To update the model entity transform for a model element element, given a matrix matrix:

  1. Let transform be a new DOMMatrixReadOnly initialized with the 16 components of matrix, with is2D set to false.

  2. Set element’s stored entity transform to transform.

This internal operation does not invoke the entityTransform setter, validate script-assigned transforms, or change the automatic fitting enabled flag. Fitting and user-agent-controlled orbit rotations MUST use this operation to expose their updated transforms. A previously returned DOMMatrixReadOnly remains unchanged when a new transform is stored.

8.2.2. Coordinate spaces and length units

The model APIs distinguish the following coordinate spaces:

model space

The resource’s coordinate space before entityTransform is applied, normalized to a right-handed, Y-up coordinate system. One unit of length in this space represents one meter of the asset’s geometry. Normalization preserves the resource’s origin; fitting does not modify this coordinate space.

element space

The coordinate space of the model element’s content box, as defined in [CSS-BOX-3]. Its origin is the center of the viewport plane, with positive X pointing right, positive Y pointing up, and positive Z pointing toward the viewer. One unit of length in this space is one CSS-derived meter, equal to 100 CSS centimeters. The fixed ratios between absolute length units in [CSS-VALUES-4], 1in = 96px = 2.54cm, give the conversion 1 CSS px = 0.0254 / 96 CSS-derived meters. This specification defines the term "CSS-derived meter"; CSS does not define an m unit.

physical presentation space

The device-dependent space in which the user agent presents the page, including any spatial or stereoscopic presentation. Its mapping from element space may depend on zoom, display characteristics, and the user agent’s presentation policy. The model APIs do not expose this mapping or guarantee a model’s physical size on the device.

The user agent MUST convert the resource’s geometry and internal transform translations to model space using the length units and axis conventions declared by the resource format, including any defaults specified by that format. If the format neither declares nor specifies default length units, one resource length unit MUST be treated as one meter.

The one-meter fallback for formats that neither declare length units nor specify default length units needs further discussion. Is one meter an appropriate default, or should a different fallback be used? See GitHub issue #155.

boundingBoxCenter and boundingBoxExtents MUST report their X, Y, and Z components in meters in model space; the homogeneous W component is dimensionless. These values MUST NOT include automatic fitting, entityTransform, CSS transforms on the element, or the mapping to physical presentation space.

entityTransform MUST map model space to element space. Its translation components are expressed in CSS-derived meters, while scale factors and rotation coefficients are dimensionless. This mapping precedes CSS transforms on the element and the mapping to physical presentation space.

Point transformation uses the transform a point with a matrix algorithm in [GEOMETRY-1]. This specification defines the coordinate spaces and length units used by the model APIs.

For fitting, the user agent MUST convert the content box’s width and height from CSS pixels to CSS-derived meters by multiplying each dimension by 0.0254 / 96. Device pixels MUST NOT be used for this calculation.

Browser zoom in this section refers to page zoom and visual viewport scaling, as distinguished in the Zooming section of [CSSOM-VIEW-1]. Page zoom affects the size of the initial viewport. Visual viewport scaling, exposed by scale, magnifies the page without affecting the initial viewport.

Page zoom and visual viewport scaling MUST NOT change the units defined above or the model-space bounds of a resource. If page zoom changes the layout dimensions used by a fitting algorithm, those dimensions MUST be converted using the same CSS-pixel conversion. This does not change when the fitting algorithms run.

The devicePixelRatio algorithm in [CSSOM-VIEW-1] uses the size of a CSS pixel at the current page zoom, with a visual viewport scale factor of 1.0, divided by the size of a device pixel. Page zoom can therefore change devicePixelRatio; visual viewport scaling is excluded from that calculation. Changes to devicePixelRatio or rasterization resolution MUST NOT change the API units, model-space bounds, or the conversion from CSS pixels to element space.

Note: These distinctions address the default length-unit question raised in GitHub issue #155. A meter of asset geometry and a CSS-derived meter of element space are not guarantees of one physical meter in the device’s presentation. The absolute-unit anchoring rules and reference pixel in [CSS-VALUES-4] explain why CSS physical units need not match physical measurements on a screen. Authors should not multiply element-space translations by devicePixelRatio.

A model-space bounding-box width of 2 represents a two-meter-wide asset, independent of fitting or zoom. A 300 CSS-pixel-wide viewport is 300 × 0.0254 / 96 = 0.079375 CSS-derived meters wide. If width limits the fit, the uniform scale is 0.079375 / 2 = 0.0396875. To move an already fitted model one CSS pixel to the right in element space, apply the translation after the existing model-to-element mapping:

const cssPixelsToMeters = 0.0254 / 96;
const translation = new DOMMatrix().translate(cssPixelsToMeters, 0, 0);
model.entityTransform = translation.multiply(model.entityTransform);

Pre-multiplying by the translation makes it element-relative rather than scaling it by the existing model fit. No device-pixel-ratio adjustment is needed.

8.2.3. Model bounds and fitting

On the initial load for a model, the user agent MUST run the bounding box calculation algorithm and store the resulting model-space bounds. The stored entity transform MUST be set so that the object is fully in view within the model element’s laid-out content box on the page. Initial fitting uses the model fit algorithm with an identity rotation in none mode, or the orbit fit algorithm in orbit mode.

The bounding box calculation algorithm consists of the following steps.

  1. With the model scene loaded and normalized to model space, set the animation to the first frame if present.

  2. let max be a new DOMPoint with values of -Infinity.

  3. let min be a new DOMPoint with values of Infinity.

  4. let queue be an empty list of elements.

  5. Add the model’s root object to queue.

  6. While queue is not empty:

    1. set element to the last element in queue and remove it from queue.

    2. If element contains any child elements, add them to queue.

    3. If element contains renderable geometry, find the minimum and maximum value for the X, Y and Z locations of that geometry.

    4. Apply the world matrix of element to the bounding box of its geometry.

    5. set each value of min to the minimum of its current value and the minimum for this element’s bounding box.

    6. set each value of max to the maximum of its current value and the maximum for this element’s bounding box.

  7. Set the values of boundingBoxCenter to be the mean of each values of min and max.

  8. Set the values of boundingBoxExtents to be each value of min subtracted from max.

The fitting algorithms MUST use the width and height of the element’s laid-out content box, converted to CSS-derived meters in element space. These dimensions result from CSS layout, using the used values defined in [CSS-CASCADE-5] and the sizing properties defined in [CSS-SIZING-3]. They are not the numerical values of the width and height attributes. CSS sizing and layout constraints can cause them to differ from the desired dimensions given by those attributes. The bounds remain in model space, before entityTransform is applied. Subsequent fitting updates MUST use the stored bounds of the loaded resource; they MUST NOT repeat the bounding box calculation algorithm or restart or seek the animation.

The model fit algorithm takes a rotation argument and consists of the following steps.

  1. Let bounds be the resource’s stored bounds, previously calculated using the bounding box calculation algorithm.

  2. Let extents be the extents of bounds.

  3. Let center be the center of bounds.

  4. Let width and height be the laid-out content-box dimensions in CSS pixels, each multiplied by 0.0254 / 96 to obtain CSS-derived meters in element space.

  5. Let xScale be width divided by extents.x, or positive infinity if extents.x is zero.

  6. Let yScale be height divided by extents.y, or positive infinity if extents.y is zero.

  7. Let scale be the minimum of xScale and yScale. If both are positive infinity, set scale to 1. If either viewport dimension is zero, set scale to 0.

  8. Let transform be a matrix with a uniform scale of scale and the supplied rotation.

  9. Set the translation in transform so that center, after applying the scale and rotation, is aligned with the center of the viewport in X and Y, and is scale × extents.z / 2 behind the viewport plane. The translation must account for the scaled and rotated position of center. With the identity rotation used for initial fitting, the front face of the scaled bounding box lies on the viewport plane and the rest lies behind it.

  10. Update the model entity transform for the model element, given transform.

Note: For initial fitting with an identity rotation, the translation in element space is (-scale × center.x, -scale × center.y, -scale × (center.z + extents.z / 2)). Scaling a model around its own origin without compensating for its scaled center would not center an off-origin asset.

8.2.4. Automatic fitting after resize

Each model element has an automatic fitting enabled flag, initially true. Beginning to load a new model resource MUST set this flag to true.

The entityTransform setter disables automatic fitting enabled only after a successful script assignment. An internal update made by a fitting algorithm MUST NOT disable automatic fitting.

Entering orbit mode MUST set automatic fitting enabled to true and apply the orbit fit algorithm. Returning from orbit to none MUST preserve the current entityTransform and leave automatic fitting enabled; changing modes back to none does not itself refit the model.

When either dimension of the loaded model element’s content box changes after layout, the user agent MUST perform the following steps:

  1. If automatic fitting enabled is false, preserve entityTransform and return.

  2. If the element is in orbit mode, apply the orbit fit algorithm, preserving the current rotation.

  3. Otherwise, apply the model fit algorithm with the current rotation as its rotation argument.

These updates SHOULD be reflected on the next rendered frame. The trigger is a change to the laid-out content-box dimensions, whether caused by width or height attributes, CSS sizing, or another layout change. Changing an attribute without changing those dimensions does not itself trigger a refit.

Note: Given that the entityTransform is determinative of the model’s fit on the page, resetting to the initial pose can be achieved by storing this initial value and re-applying it at any point in the future. In none mode, re-applying that value through script also disables automatic fitting until orbit mode is entered or a new model resource begins loading.

8.2.5. Orbit fit

The orbit fit algorithm is used when the model’s stagemode enters orbit mode and for automatic fitting while that mode is active.

The orbit fit algorithm consists of the following steps.

  1. Let bounds be the resource’s stored bounds, previously calculated using the bounding box calculation algorithm.

  2. Let extents be the extents of bounds.

  3. Let center be the center of bounds.

  4. Let diameter be the Euclidean length of extents: sqrt(extents.x² + extents.y² + extents.z²). This is the diameter of a sphere centered on center that encloses the bounding box.

  5. Let width and height be the laid-out content-box dimensions in CSS pixels, each multiplied by 0.0254 / 96 to obtain CSS-derived meters in element space.

  6. Let scale be the minimum of width and height, divided by diameter. If diameter is zero, set scale to 1. If either viewport dimension is zero, set scale to 0.

  7. Let transform be a matrix preserving the rotation of the model’s current stored entity transform and using a uniform scale of scale.

  8. Set the translation in transform so that center, after applying the scale and rotation, is aligned with the center of the viewport in X and Y, and is scale × diameter / 2 behind the viewport plane. The translation must account for the scaled and rotated position of center, so that the enclosing sphere lies entirely behind the viewport plane.

  9. Update the model entity transform for the model element, given transform.

  10. Apply subsequent orbit rotations about this fitted center, preserving its position. Reflect each resulting matrix by updating the model entity transform for the model element, given that matrix. The enclosing sphere then remains within the viewport at any orientation.

8.3. Embedded content

8.3.1. Replaced-element sizing

For CSS layout, a model element MUST be treated as a replaced element unless it represents fallback content. When it represents fallback content, it MUST be treated as an ordinary element, following HTML’s embedded-content rendering rules for object.

When replaced, its used width and height follow the CSS sizing rules for replaced elements in [CSS2] and [CSS-SIZING-3], with natural dimensions determined below. Its default object size is 300 CSS pixels wide and 150 CSS pixels high, as for video in [HTML]. Object sizing follows CSS Images 3 § 4 Sizing Images and Objects in CSS.

The width and height attributes MUST map to the corresponding CSS dimension properties and to aspect-ratio according to HTML’s dimension-attribute rendering rules for video.

To determine model natural dimensions for a model element element:

  1. If element represents its poster frame, return that image’s natural dimensions.

  2. Otherwise, return no natural dimensions.

The user agent MUST use determine model natural dimensions when sizing the replaced element. Model geometry, model-space bounds, and entityTransform MUST NOT supply natural CSS dimensions.

Whether a model element is exposing a user interface is not expected to affect the size of the rendering; controls are expected to be overlaid above the page content without causing any layout changes, and may disappear when the user does not need them.

8.3.2. Poster display

For poster display, model content is available when the selected model resource is loaded, processed, and ready to display, the condition used to resolve ready. Beginning to load a new model resource makes the previous resource unavailable for the purposes of these display rules.

A model element MUST represent the content given by the first matching condition below:

  1. If model resource loading is permitted is false, one or more model sources were specified but source selection has finished without finding a supported resource, or the selected model resource cannot be loaded or decoded, the element represents its fallback content.

  2. Otherwise, if model content is available, the element represents that model content.

  3. Otherwise, if its poster frame is not null, the element represents that poster frame.

  4. Otherwise, the element represents transparent black with no natural dimensions.

The absence of a model source alone MUST NOT be treated as a load failure for these display rules. A poster can therefore be displayed before a model source is provided.

When the element represents its fallback content, it MUST NOT also display its poster frame. If no fallback content is provided, the element represents nothing. Beginning a new model load MUST re-evaluate these display rules; a failure of a previous load MUST NOT prevent the new load’s poster from displaying.

Pausing, seeking, looping, or resetting a model’s animation MUST NOT, by itself, cause the poster to be displayed again. A paused model MUST continue to display its current pose.

When a model element represents its poster frame, the image is expected to be rendered at the largest size that maintains its aspect ratio without being taller or wider than the model element itself, and is expected to be centered in the model element. The poster MUST NOT affect the model’s bounding box or entityTransform.

Note: The poster is a loading preview, whereas fallback content is an alternative when the model cannot be displayed. A poster failure does not constitute a model failure. Posters are ordinary images; the secure-context restriction on 3D model resources and environment maps does not prevent their retrieval. Their requests remain subject to § 16.2 CORS, § 16.4 Content Security Policy, and the mixed-content checks in [MIX].

9. Events

The environmentMapReady Promise resolves when an environment map resource has been loaded, or is rejected if the resource is unable to be loaded.

The model element emits a ready Promise when the model is processed and ready to display. The Promise is rejected if the model source cannot be loaded.

16. Security considerations

16.1. Secure contexts

For the secure-context checks in this section, model resource loading is permitted for a model element if and only if its node document’s relevant settings object is a secure context. The user agent MUST use the secure context definition in [HTML] to evaluate this condition.

User agents MUST NOT fetch, decode, or render 3D model resources or author-provided environment maps for a model element unless model resource loading is permitted for that element.

Before starting a model or environment-map load for a model element, the user agent MUST check whether model resource loading is permitted for that element. If it is not, the user agent MUST NOT start the load and MUST block model resource loading for the element.

The adopting steps for a model element, given node and oldDocument, are:

  1. If model resource loading is permitted is false for node, block model resource loading for node.

To block model resource loading for a model element element, the user agent MUST run the following steps:

  1. Abort any pending model or environment-map fetch and decoding operations for element, and MUST NOT start new ones while loading remains blocked.

  2. Stop rendering element’s model and environment map, including any previously loaded content.

  3. Reject any unsettled ready and environmentMapReady promises of element, if they exist, with a SecurityError exception.

  4. Make element represent its fallback content instead of the model.

Before an initial load, an insecure context prevents fetching and decoding from starting; there are no pending operations to abort. The cancellation and rendering-stop requirements also cover a model that began loading in a secure document and was subsequently adopted into an insecure document.

Same-origin documents can have different secure-context status. For example, an HTTPS iframe embedded in an HTTP page is not a secure context because of its insecure ancestor. That iframe can open a same-origin HTTPS popup, which is a secure context because it is top-level. If opener access is retained, the popup can move an already-loading model into the iframe using window.opener.document.body.append(model). DOM adoption changes the model’s node document to the iframe’s document, so loading that was initially permitted must now be stopped. See [SECURE-CONTEXTS] for the distinction between secure contexts and potentially trustworthy origins.

The restriction does not prevent fallback descendants from rendering or loading their own resources under the normal rules for those HTML elements.

The [SecureContext] annotation on HTMLModelElement restricts exposure of the interface and its members according to [WEBIDL]. It does not replace the loading and rendering checks above. In particular, a model created in a secure document MUST NOT continue loading or rendering after being adopted into an insecure document. These checks MUST also be applied before rendering a model.

Requests for model resources and author-provided environment maps MUST follow [FETCH] and be subject to the mixed-content checks in [MIX]. Being in a secure context does not bypass those checks or other applicable resource-loading policies. The secure-context requirement itself is not a scheme whitelist for resource URLs.

Note: Secure contexts normally use HTTPS, but the standard also recognizes potentially trustworthy local origins. For example, http://localhost, http://127.0.0.1, and http://[::1] can qualify without a development certificate. The usual secure-context rules, including ancestor-context checks, still apply. Authors can check isSecureContext rather than inspecting the URL scheme.

16.2. CORS

Model resources, author-provided environment maps, and posters MUST be loaded using Fetch. Before fetching each request, the user agent MUST configure a model request given the request and the element.

To configure a model request, given a request request and a model element element:

  1. Set request’s client to element’s node document’s relevant settings object.

  2. Set request’s mode to "cors".

  3. Set request’s credentials mode to the CORS settings attribute credentials mode of element’s crossorigin attribute.

  4. Set request’s initiator type to "model".

Note: This follows the request setup used by HTML module-script fetching and the font-fetching requirements in [CSS-FONTS-4]. Same-origin blob: URLs remain usable, subject to [FETCH] and the document’s CSP.

16.3. Model resource dependencies

As specified in § 2.4 Subresource loading, model resources MUST be self-contained. Parsers and renderers MUST NOT retrieve external dependencies; a model requiring them MUST fail to load. Embedded textures do not cause separate requests and are covered by the model resource’s CSP check.

16.4. Content Security Policy

Model resource requests MUST use destination "model", which this specification adds to the destination type and RequestDestination enumeration in [FETCH]. The Fetch algorithm applies the request client’s CSP as defined by [CSP3]. In CSP’s Get the effective directive for request algorithm, "model" MUST be handled together with "audio", "track", and "video", returning media-src. Environment-map and poster requests MUST use the existing "image" destination and img-src mapping.

16.4.1. Fetch failures

A model or environment-map load that encounters a network error from Fetch MUST reject its own unsettled ready or environmentMapReady promise, respectively, with a TypeError exception. Model failures follow § 8.3.2 Poster display; poster failures follow determine a model poster frame. A failure MUST affect only the load that initiated the request.

17. Accessibility

We need to figure out how to make model accessible on a number of different fronts: • Visual: describe what is being presented over time. • Interaction: describe what can interacted with (regions, buttons, etc.). • auditory: describe audio and possibly spoke sounds, potentially over time. Conformance

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
