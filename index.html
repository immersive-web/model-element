Abstract

The model element allows embedding 3D graphical content inline within an [HTML] document to be managed declaratively, and rendered directly by the user agent. The HTMLModelElement interface then provides a simple API for controlling the presentation, animation, interaction, fetching, and UI affordances of a model.

1. Introduction

The HTML model element allows a website to embed interactive 3D models as conveniently as any other visual media. Models are served as a standalone resource. The model element also has support for interaction and animation playback while presented within the page, and supports more spatial experiences, such as the stereoscopic display of 3D content where available.

As model is rendered directly by the user agent, it has the ability to utilize privileged information, such as the user’s head and eye position or the lighting of the user’s environment, without exposing that information to JavaScript. Additionally, the use of accessibility information and controls can be engaged in a privacy-preserving manner.

As model is embedded content, the user agent can present 3D content in a privacy-preserving, interactive, and accessible manner.

2. Out of scope

There are a number of specified non-goals for this initial incubation; some are beyond the long-term scope of this proposal, and others are deferred for the benefit of reaching consensus on an initial specification, which can hopefully serve the needs of users and authors sooner.

2.1. Scene graph inspection and manipulation

While the use cases for inspecting and manipulating the contents of a given model asset are clear, the initial scope of this proposal is intentionally limited to a reduced complexity, hopefully making the initial specification one that has broad consensus amongst the web community.

2.2. Animation mixing and blending

While many popular model formats include the ability to encode, play and mix multiple animations in an animation mixing system, This initial specification considers only a single animation timeline, both for simplicity and for having a minimal viable specification on which the web community can build on.

2.3. Stateful interaction with model contents

While many popular model formats support tapping on a 3D button inside their contents to show or hide additional contents like a title, play an animation or undertake some other stateful action. Because there is no current intention to provide a JavaScript-facing mechanism to be aware of such actions, stateful interactions should be considered out of scope.

2.4. Subresource loading

While many popular model formats support the use of external asset requests for better re-use and consistency, this initial specification will only allow assets that are self-contained.

3. Examples

3.1. Adding a model to a document

The following example shows the simplest way to add a 3D model to a document:

<model src="3d-assets/car"></model>

By using content negotiation the user agent relies on the server to send back a 3D model in a format the user agent supports.

3.2. Enabling orbit stage mode

The following example shows the syntax for enabling the standard "orbit" mode:

<model stagemode="orbit">
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
</model>

3.3. Supporting multiple formats

The following example shows a list of potential source formats that can be selected from:

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
</model>

model source selection follows video selection, where the top-level src attribute takes precedence if present, followed by the first compatible source element encountered.

3.4. Providing fallback content for legacy user agents

The following example supplies fallback content for user agents that do not yet support the element:

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.pixar.usd">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
  <img src="image-assets/teapot.png">
</model>

3.5. Making model accessible

The following example supplies alt text information for both the model content and fallback content, in the event that model is not supported on the target user agent.

<model>
  <source src="3d-assets/teapot.usdz" type="model/vnd.usdz+zip">
  <source src="3d-assets/teapot.glb" type="model/gltf-binary">
  <img src="image-assets/teapot.png" alt="A teapot">
</model>

7. Interaction

In addition to emitting standard input events, model may interpret input events according to specific stage modes, including none and orbit.

7.1. none

The default value for stageMode. In this this mode, input events do not have any direct action on the behavior of the element.

7.2. orbit

In this mode, input events in a horizontal direction result in a rotation of the model about the Y axis, and events in a vertical direction result in a rotation about the horizontal axis. This is reflected in the model’s entityTransform value.

In this mode, the entityTransform value is read-only.

Setting the mode to orbit results in a change of the position and scale to the orbit fit mode.

glTF is not a run-time format. It does not define what an application should do with a model once it is loaded and rendered. It does provide some capabilities that a run-time engine may use to enhance the user experience. glTF currently does not store any interactivity information. Currently that is solely a run-time determination. The run-time determines what parts (if any) of the model may be active and the behavior based on any trigger. Like Interactivity, animation is not built-into glTF. glTF files may contain animation parameters that specify the type of animation (e.g., morph, skin & bones, etc.) and the associated parameters needed to perform the animation. There is nothing in the glTF specification that defines how one animation interacts with another. For example, a human model may include walk, jump, and drop animations; but it is unlikely that they should all be played at the same time. Any HTML element that wishes to handle animation as stored in a glTF file needs to understand how the content creator intended the animation to play. GitHub issue #2: Dealing with format specific animations and Interaction.

8. Controls

As with other media elements (again #13), having "controls" for media specific things can be extremely helpful for accessibility (and just generally helpful for developers not needing to deal with things like the fullscreen API). It would be nice to consider adding support for controls and then leaving it mostly to the UA as to what those controls are... we could figure out a standard set of things, like video provides. 9. Rendering

The model SHOULD be rendered according to a realtime, physically-based rendering (PBR) shading model, and lit by an image-based light.

9.1. Environment map

If provided, an environment map MUST be interpreted as an equirectangular environment map. If an environmentMap is not specified, the User Agent MUST provide an appropriate map.

9.2. Model pose

The position, rotation, and scale of a displayed model MUST present its contents according to its entityTransform property, a DOMMatrixReadOnly that can be composed using that object’s existing API.

The point and matrix interfaces and their operations are defined in [GEOMETRY-1].

Updates to the entityTransform SHOULD be reflected on the next rendered frame.

9.2.1. Coordinate spaces and length units

The model APIs distinguish the following coordinate spaces:

model space

The resource’s coordinate space before entityTransform is applied, normalized to a right-handed, Y-up coordinate system. One unit of length in this space represents one meter of the asset’s geometry. Normalization preserves the resource’s origin; fitting does not modify this coordinate space.

element space

The coordinate space of the model element’s content box, as defined in [CSS-BOX-3]. Its origin is the center of the viewport plane, with positive X pointing right, positive Y pointing up, and positive Z pointing toward the viewer. One unit of length in this space is one CSS-derived meter, equal to 100 CSS centimeters. The fixed ratios between absolute length units in [CSS-VALUES-4], 1in = 96px = 2.54cm, give the conversion 1 CSS px = 0.0254 / 96 CSS-derived meters. This specification defines the term "CSS-derived meter"; CSS does not define an m unit.

physical presentation space

The device-dependent space in which the user agent presents the page, including any spatial or stereoscopic presentation. Its mapping from element space may depend on zoom, display characteristics, and the user agent’s presentation policy. The model APIs do not expose this mapping or guarantee a model’s physical size on the device.

The user agent MUST convert the resource’s geometry and internal transform translations to model space using the length units and axis conventions declared by the resource format, including any defaults specified by that format. If the format neither declares nor specifies default length units, one resource length unit MUST be treated as one meter.

The one-meter fallback for formats that neither declare length units nor specify default length units needs further discussion. Is one meter an appropriate default, or should a different fallback be used? See GitHub issue #155.

boundingBoxCenter and boundingBoxExtents MUST report their X, Y, and Z components in meters in model space; the homogeneous W component is dimensionless. These values MUST NOT include automatic fitting, entityTransform, CSS transforms on the element, or the mapping to physical presentation space.

entityTransform MUST map model space to element space. Its translation components are expressed in CSS-derived meters, while scale factors and rotation coefficients are dimensionless. This mapping precedes CSS transforms on the element and the mapping to physical presentation space.

Point transformation uses the transform a point with a matrix algorithm in [GEOMETRY-1]. This specification defines the coordinate spaces and length units used by the model APIs.

For fitting, the user agent MUST convert the content box’s width and height from CSS pixels to CSS-derived meters by multiplying each dimension by 0.0254 / 96. Device pixels MUST NOT be used for this calculation.

Browser zoom in this section refers to page zoom and visual viewport scaling, as distinguished in the Zooming section of [CSSOM-VIEW-1]. Page zoom affects the size of the initial viewport. Visual viewport scaling, exposed by scale, magnifies the page without affecting the initial viewport.

Page zoom and visual viewport scaling MUST NOT change the units defined above or the model-space bounds of a resource. If page zoom changes the layout dimensions used by a fitting algorithm, those dimensions MUST be converted using the same CSS-pixel conversion. This does not change when the fitting algorithms run.

The devicePixelRatio algorithm in [CSSOM-VIEW-1] uses the size of a CSS pixel at the current page zoom, with a visual viewport scale factor of 1.0, divided by the size of a device pixel. Page zoom can therefore change devicePixelRatio; visual viewport scaling is excluded from that calculation. Changes to devicePixelRatio or rasterization resolution MUST NOT change the API units, model-space bounds, or the conversion from CSS pixels to element space.

Note: These distinctions address the default length-unit question raised in GitHub issue #155. A meter of asset geometry and a CSS-derived meter of element space are not guarantees of one physical meter in the device’s presentation. The absolute-unit anchoring rules and reference pixel in [CSS-VALUES-4] explain why CSS physical units need not match physical measurements on a screen. Authors should not multiply element-space translations by devicePixelRatio.

A model-space bounding-box width of 2 represents a two-meter-wide asset, independent of fitting or zoom. A 300 CSS-pixel-wide viewport is 300 × 0.0254 / 96 = 0.079375 CSS-derived meters wide. If width limits the fit, the uniform scale is 0.079375 / 2 = 0.0396875. To move an already fitted model one CSS pixel to the right in element space, apply the translation after the existing model-to-element mapping:

const cssPixelsToMeters = 0.0254 / 96;
const translation = new DOMMatrix().translate(cssPixelsToMeters, 0, 0);
model.entityTransform = translation.multiply(model.entityTransform);

Pre-multiplying by the translation makes it element-relative rather than scaling it by the existing model fit. No device-pixel-ratio adjustment is needed.

9.2.2. Model bounds and fitting

On the initial load for a model, the user agent MUST run the bounding box calculation algorithm and store the resulting model-space bounds. The entityTransform MUST be set so that the object is fully in view within the model element’s laid-out content box on the page. Initial fitting uses the model fit algorithm with an identity rotation in none mode, or the orbit fit algorithm in orbit mode.

The bounding box calculation algorithm consists of the following steps.

  1. With the model scene loaded and normalized to model space, set the animation to the first frame if present.

  2. let max be a new DOMPoint with values of -Infinity.

  3. let min be a new DOMPoint with values of Infinity.

  4. let queue be an empty list of elements.

  5. Add the model’s root object to queue.

  6. While queue is not empty:

    1. set element to the last element in queue and remove it from queue.

    2. If element contains any child elements, add them to queue.

    3. If element contains renderable geometry, find the minimum and maximum value for the X, Y and Z locations of that geometry.

    4. Apply the world matrix of element to the bounding box of its geometry.

    5. set each value of min to the minimum of its current value and the minimum for this element’s bounding box.

    6. set each value of max to the maximum of its current value and the maximum for this element’s bounding box.

  7. Set the values of boundingBoxCenter to be the mean of each values of min and max.

  8. Set the values of boundingBoxExtents to be each value of min subtracted from max.

The fitting algorithms MUST use the width and height of the element’s laid-out content box, converted to CSS-derived meters in element space. These dimensions result from CSS layout, using the used values defined in [CSS-CASCADE-5] and the sizing properties defined in [CSS-SIZING-3]. They are not the numerical values of the width and height attributes. CSS sizing and layout constraints can cause them to differ from the desired dimensions given by those attributes. The bounds remain in model space, before entityTransform is applied. Subsequent fitting updates MUST use the stored bounds of the loaded resource; they MUST NOT repeat the bounding box calculation algorithm or restart or seek the animation.

The model fit algorithm takes a rotation argument and consists of the following steps.

  1. Let bounds be the resource’s stored bounds, previously calculated using the bounding box calculation algorithm.

  2. Let extents be the extents of bounds.

  3. Let center be the center of bounds.

  4. Let width and height be the laid-out content-box dimensions in CSS pixels, each multiplied by 0.0254 / 96 to obtain CSS-derived meters in element space.

  5. Let xScale be width divided by extents.x, or positive infinity if extents.x is zero.

  6. Let yScale be height divided by extents.y, or positive infinity if extents.y is zero.

  7. Let scale be the minimum of xScale and yScale. If both are positive infinity, set scale to 1. If either viewport dimension is zero, set scale to 0.

  8. Set entityTransform to a uniform scale of scale and the supplied rotation.

  9. Translate the model so that center, after applying the scale and rotation, is aligned with the center of the viewport in X and Y, and is scale × extents.z / 2 behind the viewport plane. The translation must account for the scaled and rotated position of center. With the identity rotation used for initial fitting, the front face of the scaled bounding box lies on the viewport plane and the rest lies behind it.

Note: For initial fitting with an identity rotation, the translation in element space is (-scale × center.x, -scale × center.y, -scale × (center.z + extents.z / 2)). Scaling a model around its own origin without compensating for its scaled center would not center an off-origin asset.

9.2.3. Automatic fitting after resize

Each model element has an automatic fitting enabled flag, initially true. Beginning to load a new model resource MUST set this flag to true.

A successful script assignment to entityTransform in none mode MUST set automatic fitting enabled to false. An update made by a fitting algorithm MUST NOT disable automatic fitting.

Entering orbit mode MUST set automatic fitting enabled to true and apply the orbit fit algorithm. Returning from orbit to none MUST preserve the current entityTransform and leave automatic fitting enabled; changing modes back to none does not itself refit the model.

When either dimension of the loaded model element’s content box changes after layout, the user agent MUST perform the following steps:

  1. If automatic fitting enabled is false, preserve entityTransform and return.

  2. If the element is in orbit mode, apply the orbit fit algorithm, preserving the current rotation.

  3. Otherwise, apply the model fit algorithm with the current rotation as its rotation argument.

These updates SHOULD be reflected on the next rendered frame. The trigger is a change to the laid-out content-box dimensions, whether caused by width or height attributes, CSS sizing, or another layout change. Changing an attribute without changing those dimensions does not itself trigger a refit.

Note: Given that the entityTransform is determinative of the model’s fit on the page, resetting to the initial pose can be achieved by storing this initial value and re-applying it at any point in the future. In none mode, re-applying that value through script also disables automatic fitting until orbit mode is entered or a new model resource begins loading.

9.2.4. Orbit fit

The orbit fit algorithm is used when the model’s stagemode enters orbit mode and for automatic fitting while that mode is active.

The orbit fit algorithm consists of the following steps.

  1. Let bounds be the resource’s stored bounds, previously calculated using the bounding box calculation algorithm.

  2. Let extents be the extents of bounds.

  3. Let center be the center of bounds.

  4. Let diameter be the Euclidean length of extents: sqrt(extents.x² + extents.y² + extents.z²). This is the diameter of a sphere centered on center that encloses the bounding box.

  5. Let width and height be the laid-out content-box dimensions in CSS pixels, each multiplied by 0.0254 / 96 to obtain CSS-derived meters in element space.

  6. Let scale be the minimum of width and height, divided by diameter. If diameter is zero, set scale to 1. If either viewport dimension is zero, set scale to 0.

  7. Preserve the model’s current rotation and replace the scale in entityTransform with a uniform scale of scale.

  8. Translate the model so that center, after applying the scale and rotation, is aligned with the center of the viewport in X and Y, and is scale × diameter / 2 behind the viewport plane. The translation must account for the scaled and rotated position of center, so that the enclosing sphere lies entirely behind the viewport plane.

  9. Apply subsequent orbit rotations about this fitted center, preserving its position. The enclosing sphere then remains within the viewport at any orientation.

9.3. Embedded content

What’s the default CSS style for a model element? Should it have a border around it? what about background color? etc. GitHub issue #27: What’s the default style?.

Whether a model element is exposing a user interface is not expected to affect the size of the rendering; controls are expected to be overlaid above the page content without causing any layout changes, and may disappear when the user does not need them.

When a model element represents a poster frame, the poster frame is expected to be rendered at the largest size that maintains the aspect ratio of that poster frame without being taller or wider than the model element itself, and is expected to be centered in the model element.

10. Events

The environmentMapReady Promise resolves when an environment map resource has been loaded, or is rejected if the resource is unable to be loaded.

The model element emits a ready Promise when the model is processed and ready to display. The Promise is rejected if the model source cannot be loaded.

12. Overlap with "media elements"

The model element shares a lot of similarities with the audio and video elements, yet it’s distinct in some ways (we need to tease these out). It’s similar in being potentially temporal multimedia content (i.e., it has audio, it potentially animates over time). We need to figure out if model sufficiently different to warrant being its own element class, or if it can reuse much of "media element"'s infrastructure. GitHub issue #13: Is model a "media element"?.

19. Accessibility

We need to figure out how to make model accessible on a number of different fronts: • Visual: describe what is being presented over time. • Interaction: describe what can interacted with (regions, buttons, etc.). • auditory: describe audio and possibly spoke sounds, potentially over time. Usually, this would be provide by the embedded format... however, it appears that both glTF and USDZ are quite limited when it comes to accessibility. As such, it may be that we need to leverage what we can from HTML + ARIA to overcome the shortcomings of these formats. We have quite a bit of precedent (e.g., from the humble, yet limited, alt attribute, to how canvas can be made accessibly, to the potential inclusion of track elements, and so on). GitHub issue #50: Accessibility of model.

We need to define how what the ARIA semantics are and what is exposed (application probably). We need to coordinate with the accessibility folks + get this added to the HTML Accessibility API Mappings. GitHub issue #39: Accessibility: ARIA integration and HTML Accessibility API Mappings.

glTF is not a run-time format. It does not define what an application should do with a model once it is loaded and rendered. It does provide some capabilities that a run-time engine may use to enhance the user experience. glTF currently does not store any interactivity information. Currently that is solely a run-time determination. The run-time determines what parts (if any) of the model may be active and the behavior based on any trigger. Like Interactivity, animation is not built-into glTF. glTF files may contain animation parameters that specify the type of animation (e.g., morph, skin & bones, etc.) and the associated parameters needed to perform the animation. There is nothing in the glTF specification that defines how one animation interacts with another. For example, a human model may include walk, jump, and drop animations; but it is unlikely that they should all be played at the same time. Any HTML element that wishes to handle animation as stored in a glTF file needs to understand how the content creator intended the animation to play. GitHub issue #2: Dealing with format specific animations and Interaction. ↵

Conformance

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
